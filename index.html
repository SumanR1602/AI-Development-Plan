How large language models work

Tokens, context windows, sampling and cost

Models read and write small pieces of text called tokens. Tokens decide what you pay, how long you wait, and how much fits in one request.

What is a token?

A token is a chunk of text: a whole word, part of a word, a number or a punctuation mark. Common words like cat are one token. Longer or rarer words are split, so unbelievable becomes about three pieces. In English, one token is about 4 characters, so 100 tokens is roughly 75 words.

Think of it like Lego. Common words are one big brick. Rare words, code and other languages are built from many small bricks, so the same idea takes more pieces.

Why token count matters

Cost

You are billed per token, for what you send and for what the model writes.

Speed

More tokens to read and write means a longer wait. The reply appears one token at a time.

Fit

Every model has a limit on tokens per request. Go past it and the request fails or text gets cut.

Context window vs conversation length

The context window is the most tokens a model can handle in one request. It holds everything together: your instructions, the chat so far, any documents, and the reply.

System prompt Chat history Documents and question Reply

The first three are input tokens. The reply is output tokens. All four share one limit.

Conversation length is different. The model has no memory between requests. Each time you press send, the app sends the whole chat again. So a long chat means a bigger request every turn, and when it no longer fits, the oldest messages must be cut or summarised.

When the window fills up

  • The model can't read past its limit. Depending on the tool, a too-big request is rejected with an error, the reply stops early, or the oldest messages are quietly dropped.
  • Chat apps usually handle this for you. They either drop the oldest messages first, or summarise them.
  • Compaction means the older part of the chat is replaced by a short summary, while recent messages are kept word for word. The chat then carries on in much less space.
  • The trade-off is that a summary keeps the main points but can lose small details from early on. Put must-keep instructions at the start of the prompt.

Temperature: how adventurous is the model?

Sampling is how the model chooses its next token. It gives every option a probability, then picks one at random, like spinning a spinner whose slices are sized by those probabilities. "Sample 20 answers" means spinning it 20 times.

Temperature sets how adventurous that pick is. At a low setting it almost always takes the top choice, so answers are steady and repeatable. At a high setting, lower-ranked choices get a chance, so answers are varied and surprising.

SettingBehaviourGood for
Low (0 to 0.3)Focused, repeatableFacts, data extraction, code
Medium (0.5 to 0.8)BalancedChat, emails, summaries
High (0.9 and up)Varied, surprisingBrainstorming, stories, slogans

Temperature changes variety, not intelligence. A related setting, top-p, simply ignores the unlikely tail of choices.

Why longer prompts and answers cost more

Every token has to be processed by the model, so more tokens means more computing, more time and more money. Output usually costs more per token than input, mainly because the model writes it one token at a time, with a full pass for each, while your input is read in one go.

cost = input tokens × input rate + output tokens × output rate
(rates are quoted per 1 million tokens)

Two details catch people out. Cached input (a repeated prefix, such as a long system prompt) is billed at a fraction of the normal rate. And hidden "thinking" tokens are billed as output.

Hallucinations and knowledge limits

A model writes what sounds likely, not what has been checked. So it can be fluent and wrong at the same time.

Why LLMs hallucinate

A hallucination is an answer that sounds confident but is wrong or made up. It happens because the model is trained to produce a believable next token. It has no built-in fact-checker and no built-in "I'm not sure" alarm. When it lacks the facts, it still has to write something, and invented text reads just as smoothly as true text.

Think of it like a bright student in an exam who skipped one chapter. Rather than leave the answer blank, they write something that sounds right. The handwriting is just as neat.

Confidence is not correctness

The tone of an answer tells you nothing about whether it is true. Try to spot which answers are wrong:

Training data vs real-time information

A model learns from text collected up to a cutoff date. After that it learns nothing new on its own. It also never saw your private files.

Everything it learned from, up to the cutoffAfter the cutoff: unknown
Real-time facts

"Who won last night's match?" or "What is the exchange rate right now?"

Private data

"Summarise our Q3 sales deck." It has never seen your files.

Exact calculation

It predicts digits rather than calculating, so long sums can be wrong.

How grounding, RAG and tools help

The fix is to bring the facts to the model instead of hoping it remembers them. RAG (retrieval-augmented generation) means: look up the relevant text first, then put it in the prompt with the question.

Without grounding

  1. You ask a question
  2. The model answers from memory only
  3. A plausible answer, unchecked

With grounding (RAG)

  1. You ask a question
  2. Search your documents, database or the web
  3. Prompt = question + the facts found
  4. The model writes the answer
  5. Answer cites its sources

With a tool (search, calculator, database)

  1. The model decides it needs a tool
  2. The app runs the tool
  3. The real result goes back into the prompt
  4. The model writes the final answer

Model families and trade-offs

Pick the cheapest model that does the job well. Think in this order: task, then model, then cost and speed.

Large vs small models

Model makers offer a family of sizes. Larger models reason better, handle subtle language and keep long, multi-step work on track, but they are slower and cost more. Smaller models are fast and cheap, and are often plenty for narrow, repeated jobs. You cannot have top capability, top speed and the lowest cost all at once.

Think of it like staffing a project. You do not ask your most senior architect to sort the inbox, and you do not hand a production outage to a new intern.

What an LLM actually does

It repeats one move: predict the next token, add it to the text, and predict again.

There is no hidden answer database and no plan written in advance. When a model "answers a question", it is asking itself, over and over: given all the text so far, which token most likely comes next? A 200-word reply is about 270 of these predictions in a row.

Think of it like your phone's keyboard suggestions, if the keyboard had read a huge slice of the internet and you kept tapping its top suggestion for a few hundred words.

  1. Prompt: your words
  2. Tokens: the text split into chunks
  3. Predict: score every possible next token
  4. Pick one token (sampling)
  5. Add it to the text, then go back to step 3

Watch the loop, one token at a time

Press Next token to run one cycle, or Play to write the whole sentence.

  1. Read the text
  2. Score every token
  3. Pick one
  4. Add it and repeat

Grey is your prompt. Colour is the model's reply.

The model's top guesses

Why such a simple mechanism can look so clever

To get good at predicting the next token across trillions of words of text and code, the model has to pick up the patterns behind that text: grammar, facts, how arguments are built, how code works. Nobody wrote those skills in by hand. They come from getting the prediction right, at huge scale.

"The capital of France is ___"

To predict well, it needs to know a fact.

"She dropped the glass, so it ___"

To predict well, it needs everyday common sense.

"If 3 pens cost 6, then 5 pens cost ___"

To predict well, it needs to follow a pattern of reasoning.

One more trick: every token it writes becomes input for the next one. So when a model writes out its steps, those steps give it working space for harder problems. That is why "think step by step" often helps.

Why understanding this helps with prompting

The model continues whatever you give it. A vague prompt has many likely continuations. A clear one has few, and one of them is what you want.

Real-world GenAI use cases

Almost every real use of GenAI is a mix of six simple jobs, wrapped in the right checks. The industry changes, the jobs stay the same.

Six jobs LLMs do well

Summarise

Long text in, short version out.

Extract

Pull names, dates and amounts out of messy text into a fixed layout.

Classify

Put an item in a category: billing, bug, urgent.

Draft

Write a first version for a person to edit: emails, notes, code.

Answer from documents

Find the right passages (RAG from Topic 2), then answer with sources.

Act with tools

Call search, a database or a calculator, then report the result.

Prompt engineering

Prompt engineering is writing instructions so the answer you want becomes the most likely one. It follows straight from next-token prediction (Topic 4).

Prompt anatomy: task, context, format and constraints

A good prompt usually has four parts:

Task

What you want done. Start with a clear verb: write, classify, summarise.

Context

What the model needs to know: who it is for, the background, the facts.

Format

The shape of the answer: an email, a table, JSON, a number of words.

Constraints

The rules: tone, length, what to avoid, "use only these facts".

Think of it like briefing a new colleague. "Please do this (task). Here is the background (context). Send it to me like this (format). And watch out for these things (constraints)."

Optional extras are a role ("You are a support agent") and examples, which come next.

    Instead of one giant prompt, split a complex job into steps. Each step does one thing, and its output feeds the next step.

    Easier to debug

    When something goes wrong, you can see which step failed.

    Cheaper

    Easy steps can use a small model (Topic 3).

    Safer

    You can add a check step before anything reaches a customer.

    The cost is more calls, more waiting, and errors that can travel down the chain, so check the output between steps.

    Prompt engineering vs context engineering

    Prompt engineering

    Example prompt:

    "Summarize this document in 5 bullet points. Focus only on financial risks."

    Think: How do I ask the model?

    Context engineering

    Context engineering focuses on what information or context you provide to the model so that it can make a good decision.

    For example, a banking chatbot might retrieve:

    Customer profile + Transaction history + Bank policies + Previous conversations + Relevant FAQs

    Then it sends this context along with the prompt.

    Think: What information should the model see before answering?

    One example, both ways

    Prompt engineering

    "Answer the customer's question professionally."

    Context engineering

    Give the AI the customer's account details, transaction history, relevant bank policy and previous conversation.

    Both go to the same model. The first only sets how to answer. The second decides what the model knows when it answers. Without the account details, it can only write a polite but generic reply, and it may guess the facts. That guessing is the hallucination problem from Topic 2. Retrieval, memory, tools and documents are how you supply the facts.

    The five sources above are a pool, not a bundle to send every time. Pick only what is relevant to this question. More text costs more (Topic 1) and can distract the model.
